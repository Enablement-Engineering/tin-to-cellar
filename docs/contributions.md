# Shared diagnostics and package sources

ZIP import with a readable manifest posts bounded JSON to `/api/labels/contributions`. It never uploads the ZIP/artwork or fetches provenance URLs. A readable manifest can contribute diagnostics when artwork is rejected. Version 2 adds origin (`pack` or `standalone`) and bounded website-validation codes/counts. Version 1 remains accepted for older clients. Invalid diagnostics do not invalidate printable labels.

D1 stores new structured reports with one-year expiry. The existing CATALOG_CONTRIBUTIONS Durable Object retains source suggestions and their 90-day freshness behavior. Legacy copying runs through the daily scheduled job or an authenticated operator action, independently of collection and export requests. Existing reports retain their original 90-day expiry. See [migration and operations](diagnostics/operations.md). Missing D1 makes new submissions return unavailable; the application does not claim successful collection.

Same-origin JSON collection retains a 64 KiB request limit and three attempts per IP per minute. Manifest SHA-256 fingerprints deduplicate imported packs. Standalone explicit submissions use a random ID stable for retries in the current tab. Neither identifies unique users. D1 diagnostic storage is no longer subject to the Durable Object's 1,000-report cap. Source capacity can still yield partial receipt: diagnostics stored, source receipt unconfirmed. Retry is safe and printing remains available.

`POST /api/labels/process-notes` receives only an explicitly shared, bounded retrospective and its parent submission ID. It requires a matching stored report revision, uses a 16 KiB limit and the collection rate limiter, and retains notes for 90 days. Retries neither create a second report nor extend expiry. Different replacement notes for the same report are rejected, not silently accepted.

`GET /api/labels/diagnostics` requires `DIAGNOSTICS_READ_TOKEN` in an Authorization Bearer header. It exports pages of up to 200 unexpired reports with optional unexpired notes; `until` fixes the receipt cutoff and `cursor` advances by stable report ID. Raw exports stay private and outside Git/Actions artifacts. The existing `GET /api/labels/contributions` admin-token export remains for legacy backfill. Never put either token in a URL.

`GET /api/labels/sources?catalogId=<existing catalog ID>` returns up to five recent source suggestions. These are untrusted agent-reported leads, not independently verified endorsements. A latest unavailable/wrong-package observation suppresses a URL. Source links can be publicly reused. Workers never fetch those URLs or store source-image copies.

The per-label `tin-to-cellar:sources` extension accepts up to ten entries with exactly `url`, `status`, `package`, and `variant`; collection adds an exact matched catalog ID. HTTPS source links cannot have query strings, fragments, credentials, explicit ports, or local/IP hosts. Custom/unmatched blends are skipped. Older package-appearance provenance becomes unverified leads. Source metadata stays separate from diagnostics; no free-text packaging analysis, private attachment metadata, filenames, or image copies are collected automatically.

Public URL filtering does not guarantee a URL path contains no personal information. Optional note validation likewise bounds structure and length, not semantic privacy. The collection notice, preview, explicit narrative-sharing action, and privacy page describe these separate boundaries.

Diagnostic note ownership uses a separate random 256-bit receipt. The browser creates it before the first contribution request and sends it in `X-Diagnostic-Capability`. Only the first inserted report stores its SHA-256 hash; duplicate requests never replace that hash. A matching capability is required for notes. The receipt survives reloads and reimports in the same tab through session storage, with an in-memory fallback, a maximum of 100 receipts, and one-year expiry. It is never added to a manifest, diagnostic JSON, public response, or private diagnostic export. Closing the tab, clearing storage, or eviction can lose it. The UI explains that the original tab is required and notes must remain local if that receipt is gone. An existing report without a capability cannot be claimed by resubmitting its ID. This proves continuity with the first submitting client, not authorship of an anonymously submitted pack.

The shared daily allowance counts reserved report/note records. Exact stored duplicates return without another reservation; competing first requests reserve the same resource atomically in the Durable Object. Conflicting reports or notes return 409. Reservations remain charged after uncertain persistence and are reused on retry during that UTC day, so there are no refund races. Old reservation keys are deleted by the daily alarm. The per-IP request limiter and bounded JSON reader still apply to duplicates. Uniquely identified anonymous reports can still fill the allowance; this protects against duplicate amplification, not anonymous-client fairness or an account-wide spending cap.
