1. Refresh `origin/main`; reconcile only owned changes and record release SHA. Verify the artwork publication slot is released or its coordinator explicitly accepts coexistence. The earlier publication hold is not assumed to have expired.
2. Inspect applied migration history and capture an approved recovery/backup reference before any remote mutation. Check for migration-number conflicts with concurrent releases. Verify existing migrations including `0005` and keep the readiness metadata scan; `0005` alone does not prove metadata backfill completion.
3. In isolated staging, apply pending gallery migrations in filename order: `0006_print_intent.sql`, then `0007_public_browse_index.sql`. `0006` adds anonymous aggregate tables and an admission counter; `0007` adds the public browse index. Neither removes data. All remote commands require separate authorization.
4. Rehearse the current workflow's catalog seed. It upserts catalog rows and alias targets, even though it does not delete gallery submissions/artwork. Compare generated canonical IDs and aliases with active artwork work before production. Do not treat an additive migration as proof that the seed step is harmless.
5. Verify old Worker reads/publication against the migrated staging schema and candidate behavior with analytics off. Establish lock/duration and failure handling for index creation. Record schema and seed results independently.
6. After staging acceptance and production authorization, use the current-main workflow. It applies diagnostics migrations, gallery migrations, catalog seed and then deploys Worker/assets. Inspect pending diagnostics migrations too; do not add an unreviewed migration to this release. Production uses reviewed repository configuration, not a stale generated release file. Preserve live gallery/agent switches and separate analytics-off settings.
7. If a migration/seed fails, stop before deploying consumers, inspect the recorded applied state and reconcile without blindly replaying SQL. If candidate behavior fails after deployment, restore a tested compatible application through the coordinated current-main release path. Preserve new tables/index and existing rows; do not run destructive down-migrations or rewind catalog data without a separately reviewed recovery action. Whole-database restore could discard artwork published after the snapshot and is not routine application rollback.
8. Record the previous production SHA/version as the rollback target only after hosted discovery and compatibility rehearsal. Base `f73760b` is not assumed to identify the live Worker. Analytics remains disabled during rollback. Verify auth, health capabilities, protected budget 403 and public serving after recovery.
